# Скорость выделения клавиш (NFR-02, NFR-03)

Замер: `npm run perf` (`e2e/perf/selection.perf.ts`). Заготовка Dota 2, профиль «Тестовый» (~80 биндов), и тот же профиль с 500 биндами (NFR-03, `e2e/perf/big-profile.ts`: добавочные действия «Действие N» по всем слоям модификаторов, без конфликтов). Окно 1920×1080, панель 800 px.

- **Рамка:** 4 прохода по 60 движений указателя по всей клавиатуре и мыши, туда и обратно. Длительность кадров считается по `requestAnimationFrame`, потому что Firefox не знает `longtask`. Отдельно — отпускание кнопки мыши.
- **Клавиши и клики** (режим «Навигация»): Ctrl+A, снятие выделения после Ctrl+A — Esc и клик по пустому месту, Shift+стрелки, клик и серия из 30 быстрых кликов по забинженным клавишам без ожидания кадра.
- **Ответ на действие** — `duration` из Event Timing API: от нажатия до отрисовки кадра после обработчика, так же браузер считает INP. Короче 16 мс браузер не сообщает — тогда 16. Есть и прежняя оценка сверху «до второго кадра» (`paint` в выводе), она включает ожидание до двух кадров; таблицы до раздела «Перед 1.0.0» — по ней.
- **Цель:** ни одного кадра дольше 50 мс на рамке, ответ на любое действие не дольше 50 мс.

Цифры зависят от машины, поэтому замер не входит в `npm run e2e`. Сравнивать нужно «до» и «после» на одной машине.

**Собранная версия**, оба браузера: `npm run build`, `npx vite preview`, затем `PERF_URL=http://localhost:4173/hotkey-map/ npm run perf`. В сборке `?storage=browser` не действует, и Chrome просит папку, поэтому при `PERF_URL` сценарий до загрузки страницы прячет `showDirectoryPicker`: приложение само уходит в запасной режим, как в Firefox. Код приложения для этого не меняется.

**Трассировка Chrome** по сценариям (JavaScript, стили, раскладка, отрисовка, Layerize): `TRACE=1 npm run perf -- --project=chromium -g trace` (`e2e/perf/trace.perf.ts`), для сборки — с тем же `PERF_URL`.

## Перед 1.0.0 (26.10.2026)

Цель — мгновенный отклик на всё, что делают с клавиатурой, мышью и панелью, в том числе на 500 биндах. Замер «до» — 281f7fd, «после» — итог всех шагов. Ответ на действие — Event Timing, мс.

### Что было не так

- **Ctrl+A и снятие выделения** монтировали в панели сотни строк сразу: разделы выделенных клавиш или полный список действий игры. На 500 биндах одно действие — около 200 мс JavaScript и 140 мс раскладки (трассировка сборки в Chrome).
- **Строки искали свои бинды перебором профиля**: 500 строк × 500 биндов.
- **Спрятанный список действий перерисовывался на каждое изменение выделения** — у строк каждый раз новые обработчики, `memo` не держался. Из-за этого даже клик и рамка на 500 биндах тратили в 2,5–4 раза больше JavaScript.
- **Отложенный рендер (`useDeferredValue`) не гарантирует, что кадр с клавиатурой будет нарисован раньше панели**: рендер успевал закончиться до отрисовки, и кадр ждал панель. Особенно заметно в Firefox.

### Шаги

| Шаг | Что сделано | Эффект (сборка) |
|---|---|---|
| 1 | Индекс биндов по действию и по клавише — один раз на версию профиля (`src/domain/bindings.ts`) | 500 биндов, Chromium: Ctrl+A 176 → 136, Esc 200 → 176; Firefox — в пределах шума |
| 2 | Список действий при выделении не размонтируется, а прячется (React `<Activity>`); поиск и вкладка ячеек сбрасываются при скрытии, как раньше при размонтировании | 500 биндов: Esc 152–200 → 128–160 |
| 3 | Отложенная панель: `useDeferredValue` (FR-13) | 500 биндов: Ctrl+A 136–224 → 48–72, Esc → 32–128 |
| 4 | Пока тянется рамка — только «Выделено: N», список строится после отпускания (FR-13) | Рамка на 500 биндах: самый долгий кадр 133–200 → 17–50, ни одного дольше 50 мс |
| 5 | `content-visibility: auto` у строк панели: строки за экраном не раскладываются и не рисуются | Chromium, 500 биндов: Esc 104 → 32, отпускание рамки 104 → 72 |
| 6 | Панель догоняет выделение после отрисовки кадра (`src/lib/use-after-paint.ts`, `startTransition`) вместо `useDeferredValue` | Firefox, 500 биндов: Esc 96–112 → 64, отпускание рамки 136–160 → 16 |
| 7 | Список действий под `memo`: спрятанный список не перерисовывается при смене выделения | Firefox, 500 биндов: Ctrl+A 56–64 → 16, серия кликов 64–72 → 24 |

**Проверено и не дало выигрыша (откачено или не делалось):**

- Перенос подписок строк на store (конфликты, захват) на уровень списка: по CPU-профилю подписки — около 2 % времени монтирования, основное — создание DOM, раскладка и стили.
- 3D: `will-change: transform` у верхних граней и у сцены. Layerize в Chrome почти не изменился (94 → 97 мс на 12 Shift+стрелок). В 3D каждая верхняя грань — свой слой композитора из-за `matrix3d`; ответ на действия при этом укладывается в 50 мс.
- История zundo, всплывающие сообщения и сессия хранения при смене выделения не работают: выделение живёт в store устройств, история — только у store данных.

### Что осталось

**Firefox, 500 биндов: Esc и клик по пустому месту сразу после Ctrl+A — 48–96 мс** (в повторах: Esc 48–64, клик 32–96). После Ctrl+A панель вставляет разделы ~75 клавиш — около 500 строк. Рендер прерывается, а вставка в DOM нет: в Firefox это один кадр около 80 мс. Сценарий замера нажимает следующее действие через ~100 мс после Ctrl+A, и оно ждёт этот кадр. Если нажать после того, как панель дорисовалась, ответ укладывается (Esc 16–48). Клавиатура подсвечивается сразу и здесь — задерживается только ответ на следующее нажатие.

Варианты, если понадобится:

1. **Строки порциями.** Панель добавляет разделы за 2–4 кадра, каждый короче 50 мс. Видимая разница: длинный список «дорастает» вниз за ~50 мс. Обсуждалось перед шагами, решено пока не делать.
2. **Виртуальный список.** Самый быстрый, но ломает поиск по странице (Ctrl+F) и переход к разделу из бокового меню — не советуем.
3. **Легче строки.** Меньше DOM на строку (иконки «⋯» и «×» через `<use>`, меньше классов) — выигрыш оценочно 10–20 %, без гарантии уложиться.
